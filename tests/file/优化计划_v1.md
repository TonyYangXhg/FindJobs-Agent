# FindJobs-Agent 优化计划 v1（精选必要项）

> 依据：Locust Baseline（1 用户）  
> - `GET /api/jobs`：中位约 **13s**，响应约 **4.5MB**，RPS≈0  
> - `POST /api/jobs/match`：耗时约 **130ms**，但响应约 **5.2MB**  
> 原则：只做能直接改善上述数字、且能写进简历的最小集合；不做 Redis / 数据库迁移 / LLM 相关改造。

---

## 任务清单

- [ ] **P1** 为 `GET /api/jobs` 增加进程内缓存（按数据文件 mtime 失效）  
  **现状问题**：每次请求都可能重新读 `jobs_enriched.csv` / `all_companies_jobs.json`，再用 pandas `iterrows` 全量组装岗位列表，导致单次约 13 秒、响应约 4.5MB。  
  **做什么**：在 `api_server.py` 增加模块级缓存（例如 `_jobs_cache`、`_jobs_cache_mtime`、`_jobs_cache_source`）；加载前比较数据文件的 `stat().st_mtime`（必要时加文件大小），未变化则直接返回缓存列表；变化时再重新解析并更新缓存。`jobs_store` 与缓存同步更新，避免 match 读到旧/空数据。  
  **验收**：同一进程内连续两次 `GET /api/jobs`，第二次延迟应从约 13s 降到毫秒～百毫秒级（若仍返回全量 4.5MB，延迟会受序列化/网络影响，但应远低于 13s）；Locust 1 用户复测记录 P50/P95。  
  **简历价值**：这是「优化前 13s → 优化后 Xs」最硬的对比数字来源。

- [ ] **P2** 为 `jobs_store` / 缓存读写加 `threading.RLock`，保证并发安全  
  **现状问题**：`jobs_store.clear()` 与 `extend()` 非原子；加压或多请求交错时，`/api/jobs/match` 可能读到空列表或半截数据。简历落盘 `_save_resumes_to_disk` 亦无锁，并发上传有丢失风险（本阶段以 jobs 为主）。  
  **做什么**：增加全局 `RLock`；所有「读 jobs_store / 写 jobs_store / 更新 jobs 缓存 / 读缓存返回」走同一把锁；保持临界区短小，避免在锁内做 LLM 或慢 IO。  
  **验收**：Locust 提到 10 用户时，`/api/jobs/match` 不再出现偶发空结果或莫名 5xx；错误率保持 0。  
  **简历价值**：能讲清「并发下共享状态的正确性」，而不只是「加了个缓存」。

- [ ] **P3** 给 `GET /api/jobs` 加分页 + 列表字段裁剪（减负，解决体积瓶颈）  
  **现状问题**：即使有缓存，每次仍序列化并传输约 4.5MB；1 用户 RPS 都接近 0，50 用户会把开发服拖死，缓存无法单独解决吞吐。  
  **做什么**：支持查询参数，例如 `page`（从 1 起）、`page_size`（默认 50，设上限如 100）；响应包含 `total`、`page`、`page_size`、`jobs`。列表项只保留匹配/展示必需字段（如 id、title、company、location、required_skills/skill 摘要、match 相关摘要字段、apply_url 等），**不要**在列表里默认返回完整 `description` / `requirements` 长文本。详情可继续用现有全量数据或后续再加 `GET /api/jobs/<id>`（本计划不强制新详情接口，前端若暂依赖全量，可保留 `?all=1` 兜底但压测与默认路径走分页）。  
  **验收**：默认分页下单次响应体积降到约数百 KB 量级；Locust 脚本改为打 `/api/jobs?page=1&page_size=50`；10 用户下 RPS 明显大于 0。  
  **简历价值**：「全量 4.5MB → 分页后 XXXKB，RPS 从≈0 提升到 Y」——比只写「加了缓存」更完整。

- [ ] **P4** 给 `POST /api/jobs/match` 增加 `top_k`（默认 20 或 50），禁止默认回传全量匹配列表  
  **现状问题**：匹配计算本身约 130ms 尚可，但响应约 5.2MB，说明把大量岗位（含冗长字段）全部返回；网络与 JSON 序列化会拖垮并发。  
  **做什么**：请求体支持 `top_k`（默认 20，上限 100）；服务端仍可对全量 jobs 计算分数，但响应只返回排序后的前 `top_k` 条；每条只保留匹配展示所需字段（id、title、company、match_score、matched/missing skills 等），去掉或截断超长 JD。响应中可增加 `total_matched` 或 `candidate_total` 便于前端展示「共匹配多少」。  
  **验收**：回包体积下降至少一个数量级；延迟不劣于当前；Locust 中该接口 P95 与平均 Size 写入对比表。  
  **简历价值**：体现「接口契约为高并发设计（Top-N），而不是把内部全量结果直接吐给客户端」。

- [ ] **P5** 更新 Locust 脚本与复测流程，产出「优化前 / 优化后」对比表并归档  
  **现状问题**：当前脚本打全量 `/api/jobs`，无法反映分页优化后的真实服务能力；没有统一存档则简历数字无法复核。  
  **做什么**：  
  1. 修改 `tests/locustfile.py`：`GET` 改为 `/api/jobs?page=1&page_size=50`；`POST /api/jobs/match` 带上 `top_k`（与默认一致）。  
  2. 固定复测参数：先 1 用户确认功能，再 **10 用户 / spawn-rate 5 / 3 分钟**（与文档一致，便于对比）。  
  3. 使用 `--csv tests/results/after`（或同等路径）导出；手填对比表：RPS、P50/P95、错误率、Average Size。  
  4. 保留优化前截图/CSV，避免只报优化后数据。  
  **验收**：`tests/results/` 下有 baseline 与 after 两套结果；对比表数字可直接粘贴进简历。  
  **简历价值**：没有这一步，P1～P4 都无法变成可信叙事。

## 明确不在 v1 范围（避免分心）

| 不做 | 原因 |
|------|------|
| Redis / 外部缓存 | 单机进程内缓存已够第一版数字 |
| gunicorn / 多进程改造 | Windows 本地别扭；有对比数字后再做 |
| Mock LLM / 简历上传压测 | 当前瓶颈在 jobs/match，与 LLM 无关 |
| matcher 算法大重构（倒排索引等） | match 已约 130ms，优先砍回包体积 |
| 面试链路并行 LLM | 属加分项，放 v2 |

---

## 建议执行顺序

```
P1 缓存 → P2 加锁 → P3 分页裁剪 → P4 match Top-N → P5 复测归档
```

完成 P1 后即可做一次「仅缓存」的 1 用户复测（可看到延迟下降）；完成 P3/P4 后再做 10 用户正式对比，作为简历最终数字。
